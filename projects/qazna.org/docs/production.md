# Производственные мощности и входные зависимости

Версия 0.4.0 добавляет проверку выполнимости выбранного производственного плана и совместный резерв мощности и входных ресурсов. Это следующий уровень модели организма: подразделение имеет функцию, ограниченную способность выполнять её и зависимости от других подразделений. Оператор выбирает процесс, период и конкретные входные партии; цель максимизации прибыли отсутствует.

## Объявления и версии

`POST /v1/production/capacities` принимает `id`, `unit` (UUID подразделения), `period` (YYYY-MM-DD), `capacity_unit`, `quantity`, `basis`. Например, кухня объявляет 120 `oven_minutes` на день. Одна комбинация подразделения, дня и кода мощности имеет одну запись. Все процессы, использующие её, разделяют общий лимит. Разные коды должны обозначать действительно независимые мощности: система пока не умеет обнаруживать, что один станок объявлен под двумя названиями.

`POST /v1/production/recipes` принимает неизменяемое описание процесса:

```json
{
  "id": "00000000-0000-0000-0000-000000000010",
  "unit": "00000000-0000-0000-0000-000000000007",
  "name": "Упаковка порции",
  "capacity_unit": "packing_minutes",
  "capacity_per_batch": "2",
  "output_category": "food",
  "output_unit": "packed_meal",
  "output_per_batch": "1",
  "inputs": [
    {"slot": "meal", "category": "food", "unit": "meal", "quantity_per_batch": "1"}
  ],
  "basis": "Экспериментальная технологическая карта, редакция 1"
}
```

`unit` верхнего уровня — подразделение; `unit` внутри входа — код физической единицы. Все количества — положительные целые числа в строках. `capacity_per_batch` и входы задаются на один полный цикл; `output_per_batch` — его ожидаемый выход. Коды входов `slot` уникальны, максимум 32. Пустой список допустим для явно заявленного исходного процесса, но не является доказательством получения ресурса без затрат.

UUID процесса служит неизменяемым идентификатором редакции. Изменённая карта получает новый UUID и основание; прежние планы сохраняют прежнюю карту. Автоматическое замещение редакций, переутверждение мощности и нормативы потребностей будут отдельными механизмами. Объявление мощности — заявление оператора, а не независимая проверка оборудования.

`GET /v1/production/capacities/{id}` возвращает объявление, `reserved` и `available`. `GET /v1/production/recipes/{id}` — полную карту процесса.

## Оценка выполнимости

`POST /v1/production/assess` принимает тот же запрос, что и создание плана:

```json
{
  "recipe": "00000000-0000-0000-0000-000000000010",
  "capacity": "00000000-0000-0000-0000-000000000009",
  "batches": "4",
  "inputs": [
    {"slot": "meal", "resource": "00000000-0000-0000-0000-000000000005"}
  ],
  "basis": "План упаковки для дальнейшего обеспечения"
}
```

Процесс и мощность должны принадлежать одному подразделению и иметь одинаковый код мощности. Для каждого входа нужна ровно одна отличающаяся от остальных партия с совпадающими категорией и единицей. Поставляющий счёт должен быть связан с подразделением. Партии могут поступать из других ветвей иерархии: производственная зависимость отличается от административной ответственности. В результате виден `supplying_unit` каждого входа.

Система не выводит взаимозаменяемость продуктов из категории: `food` и `gram` ещё не описывают состав или качество. Подходящую партию явно выбирает оператор. Разделение одного входа на несколько партий и использование одной партии в нескольких входах пока не поддерживаются; общую потребность в таком ресурсе следует указать одним входом карты. Преобразование единиц не выполняется.

Оценка возвращает:

- `max_batches`: минимум целых циклов, допускаемых свободной мощностью, каждым выбранным входом и числовым пределом выхода;
- `planned_output`: ожидаемое количество при запрошенном числе циклов;
- `capacity_required`, `capacity_available`;
- для каждого входа — `required`, `available`, `shortage` в его собственной единице;
- `feasible` и причины `capacity_shortage`, `input_shortage`, `quantity_limit`.

Например, при 12 свободных минутах, затратах 2 минуты на цикл и запасе воды на 4 цикла максимум равен 4. Добавление учётной меры не увеличивает этот физический предел. Остатки денег и учётные нормативы в оценке не используются.

Оценка читает согласованный снимок PostgreSQL REPEATABLE READ и ничего не резервирует. Её результат может устареть сразу после ответа. Числа расчёта используют i128 и передаются строками: даже переполнение допустимого i64 запаса отображается точным требуемым количеством, но такой план блокируется. `max_batches` относится только к выбранным партиям и мощности, а не к оптимальному плану всей системы.

## Резерв производственного плана

`POST /v1/production/plans` принимает тот же запрос с `Idempotency-Key`. Под блокировками заново проверяются мощность и партии. Успех возвращает `status = reserved`, `plan_id` и снимок оценки до резервирования. В одной транзакции резервируются мощность и все входы. Денежные проводки не создаются.

Нехватка возвращает HTTP 200, `status = blocked`, `plan_id = null` и снимок причин. Этот результат сохраняется в общем журнале команд; повтор ключа возвращает прежнее наблюдение, даже если условия изменились. Для новой оценки с резервированием нужен новый ключ. Ошибки структуры, несовместимые единицы и технический сбой откатываются без расходования ключа. Порядок входов не меняет смысл повторного запроса.

`GET /v1/production/plans/{id}` показывает исходный запрос, ожидаемый выпуск и актуальное состояние `reserved` или `cancelled`. `POST /v1/production/plans/{id}/cancel` принимает `basis` и ключ команды; отмена освобождает все входы и мощность вместе. История сохраняется. Повтор того же ключа безопасен; повторная отмена новым ключом даёт 409.

Поле `reserved` обычного `/v1/resources/{id}` теперь включает и резервы жителям, и производственные резервы. Поэтому один ресурс нельзя одновременно обещать жителю и производству. Даже планы разных дат используют один реальный запас; будущие поступления пока не учитываются. Период — календарный день мощности, а не расписание внутри дня. Резервы не истекают автоматически.

## Гарантии и пределы

Миграция 0004 сохраняет предыдущие миграции и действующие резервы. Записи неизменяемы, дочерние входы нельзя добавлять к ранее сохранённой карте или плану. Отложенные ограничения БД проверяют полноту входов, точные коэффициенты, соответствие мощности и общий физический остаток. Прикладной порядок блокировок: ключ команды → план при отмене → мощность → партии по UUID. Производство не блокирует счета, поэтому не вводит обратный порядок по отношению к выдаче жителям.

План — обещание использования входов, не подтверждённое производство. Его выход не добавляется в `resources`, не уменьшает неудовлетворённую потребность и не даёт основания для эмиссии. Нет списания производственных входов, подтверждения выхода, потерь, брака, замещения, складских перемещений и транспорта. Нет автоматического приоритета производства перед выдачей жителям: резерв получает первая успешно завершённая команда.

Цепочки пока строятся только от существующих партий. Ожидаемый выход другого плана не является доступным входом; циклические обещания не создают запас. Полный граф технологий, несколько общих мощностей на процесс и автоматический подбор плана по потребностям — следующие задачи. Все маршруты требуют существующий локальный операторский токен.
