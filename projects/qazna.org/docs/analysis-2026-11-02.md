# Предварительный анализ Qazna

Исторический план на начало реализации 2 ноября 2026. Текущее состояние см. в [README](../README.md).

Дата: 2 ноября 2026 года. Целевой срок демонстрации: 16 ноября 2026 года, указанный автором как срок рассмотрения обращения eGov/eOtinish.

Название проекта — **Qazna**, основное имя — **qazna.org**. Экономическая модель — Теңге из книги «Тартар и Я». Предшествующий код находится в отдельном исходном репозитории Qazna; эта папка содержит новое Rust-приложение, миграции PostgreSQL, тесты и план его развития. Указание имени не означает выполненную публикацию сайта или проверку владения доменом.

## Решение для первого этапа

Подготовить исследовательский MVP с синтетическими жителями, физическими ресурсами и проверяемым денежным учётом. К 16 ноября целиться в воспроизводимую демонстрацию одного полного хозяйственного цикла и его сбоев. Работающая симуляция проверяет следствия выбранных правил; она не доказывает применимость системы к национальной экономике. Срок рассмотрения обращения не означает согласование государственного пилота.

По решению автора от 2 ноября MVP сразу строится на том же стеке, который планируется для промышленной версии: Rust + Tokio + Axum + SQLx + PostgreSQL. Python остаётся расчётным модулем, React/TypeScript — будущим интерфейсом. Временная реализация на Go с последующим переписыванием исключена. Старый Qazna используется как источник требований и сценариев проверки.

Реализован первый модуль: постоянный журнал, точные денежные суммы, атомарные переводы, идемпотентность и локальный HTTP API. [Архитектура](architecture.md) описывает решения и ограничения; [инструкция запуска](development.md) содержит команды и примеры. Полный экономический MVP ещё не завершён.

## Основания и проверка расчётов

Основные источники:

- [Публикация книги](../../../book/README.md).
- [Экономическая модель](../../../research/МОДЕЛЬ_ЭКОНОМИКИ_ТЕҢГЕ.md), особенно разделы о денежном обороте, архитектуре и выполненных десятисекторных расчётах.
- [Расчётный код](../../../research/scripts/tenge_circulation_model.py) и [сохранённые результаты](../../../research/tenge_calculations.json).
- Старый Qazna: `STANDARD/NON_GOALS.md`, `STANDARD/TRANSACTION_SEMANTICS.md`, `internal/ledger`, `internal/store/pg`, `internal/governance`, `internal/audit`, `cmd/api/main.go`, `core/ledger`, `web/package.json`, `web/docs/adr/0002-core-ledger-rust.md`.

При повторном расчёте 2 ноября внутренние проверки основного и расширенного режима прошли. С сохранённым JSON сопоставлены 4762 числовых значения: различий при относительном допуске 1e-10 и абсолютном 1e-8 не обнаружено. Использовано существующее временное окружение `/private/tmp/tenge-research-venv`; исходные результаты не перезаписывались.

Десятисекторная модель уже решается HiGHS. Это пятилетняя линейная модель с условными отраслевыми наборами, ценами и мощностями. Старое замечание об отсутствии решателя в четырёхсекторном примере не описывает текущее состояние десятисекторного расчёта. Дробные значения мощностей и штата в LP не заменяют отдельного расчёта неделимых объектов. Коэффициент покрытия потребностей не равен доле людей, которым разрешено отказать в обеспечении.

Существенный открытый вопрос уже виден в коде: после оборота начальных 1000 единиц и сохранения 100 у жителей в казне остаётся 900. Следующее назначение 1000 невозможно из этого остатка. Физическая выполнимость годового плана сама по себе не обеспечивает ежедневную ликвидность казны. Автоматически закрывать этот разрыв эмиссией нельзя, если выбранные правила разрешают эмиссию только при подтверждённом росте.

## Что даёт старый Qazna

| Компонент | Вывод для MVP |
| --- | --- |
| Go API, PostgreSQL, проводки, роли, аудит, governance, тесты | Источник требований и тестовых сценариев; Go не включается в новый runtime |
| Rust ledger | Есть исполняемый код, пакетные движения, журнал событий, снимки и тесты. Это не просто архитектурное обещание |
| Выбор реализации в `cmd/api/main.go` | Удалённое ядро выбирается по gRPC-настройке, иначе PostgreSQL, иначе память. Наличие подключённой БД не означает, что удалённое ядро хранит в ней свои операции |
| Хранение Rust | В просмотренной реализации используется файловый журнал и снимки. `flush()` не даёт тех же гарантий восстановления, что отдельно проверенная схема долговечности записи |
| Семантика казны | Обычный `Transfer` в Go запрещает списание со счёта Treasury и допускает комиссии. Для Теңге нужен отдельный разрешённый сценарий назначения средств и запрет комиссий в экономическом профиле |
| Повторные запросы | В просмотренных путях ключ идемпотентности возвращает прежнюю операцию. Нужно сравнивать также содержимое запроса и отклонять повтор ключа с другими параметрами |
| Пакетные списания | Go InMemory проверяет каждое движение до применения всей группы. Проверить отдельным тестом несколько списаний с одного счёта, суммарно превышающих остаток; не переносить эту логику без проверки |
| Детализация Rust через gRPC | Есть TODO для dimensions и detailed balances. Нельзя считать Go и Rust полностью эквивалентными |
| `web` | По package.json это сайт документации на VitePress. Пользовательские экраны экономического MVP потребуют отдельной реализации |
| Стандарт Qazna | В NON_GOALS прямо исключены денежная политика и потребительский кошелёк. Модель Теңге следует оформить отдельным прикладным профилем |

Обзор старого репозитория был предварительным, не полным аудитом безопасности. Его Go-тесты остановились до выполнения из-за несовместимости установленного инструментария; его Rust-тесты не запускались. Новый Rust-модуль в этой папке имеет собственные проверки с реальной PostgreSQL, запускаемые через `scripts/check.py`.

## Технологический стек

| Слой | Выбор для MVP | Причина |
| --- | --- | --- |
| API и хозяйственные операции | Rust + Tokio + Axum | Одно ядро для MVP и дальнейшего промышленного развития |
| Постоянные данные | PostgreSQL + SQLx, одна основная БД | Атомарное сохранение проводок, резервов, состояния операции и задания на дальнейшую обработку |
| Расчёты | Python, NumPy, SciPy HiGHS | Повторное использование уже воспроизводимой математической модели |
| Пользовательский интерфейс | React + TypeScript + Vite | Кабинет жителя, панель хозяйства и журнал аудита в одном веб-приложении |
| Обмен с расчётами | Задания в PostgreSQL и Python worker | Для MVP достаточно таблицы заданий, версий входных данных и результатов; отдельный брокер не нужен |
| Документация | Markdown в репозитории; VitePress при публикации | Решения по архитектуре, правила профиля Теңге и воспроизводимый запуск |
| Развёртывание | Сначала локально, затем воспроизводимая упаковка | Docker сейчас недоступен как команда; установленный PostgreSQL позволяет подготовить отдельную тестовую БД без изменения действующих баз |
| ИИ | Необязательный помощник по объяснению результатов | Расчёт выполнимости выполняет решатель; ИИ не подписывает проводки и не принимает решения об эмиссии |

Ядро с первого этапа реализуется на Rust. Срок достигается ограничением числа хозяйственных сценариев. Сам выбор языка не обеспечивает правильность денежной политики, поэтому правила и инварианты проверяются отдельно. PostgreSQL и HTTP API используются уже в первом рабочем модуле, без временного хранения денежных остатков в памяти.

Для денежных сумм используются целые минимальные единицы с явной проверкой переполнения. В новом модуле сумма операции ограничена положительным i64, обычный баланс — неотрицательным i64; суммирование проводок в PostgreSQL использует numeric. Экономический масштаб минимальной единицы ещё предстоит определить. В JSON передавать суммы строками, чтобы избежать потери точности JavaScript. Значения с плавающей точкой допустимы в оптимизации, но результат перед проводкой должен пройти округление по заданному правилу и повторную проверку ограничений.

Транзакционная изоляция требует осмысленного выбора и повторения всей транзакции при соответствующих конфликтах; одного названия уровня недостаточно. См. [документацию PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html). Возможности решателя описаны в [документации SciPy HiGHS](https://docs.scipy.org/doc/scipy/reference/optimize.linprog-highs.html).

## Обязательный объём демонстрации

Один условный населённый пункт, 100 синтетических жителей, три направления — питание, вода и энергия; 30 моделируемых дней. Это новое явно описанное учебное хозяйство. Нельзя получить его простым делением пятилетней модели для большого населения: другие единицы, период и инфраструктура должны быть заданы отдельно.

Пятилетний десятисекторный расчёт сохранить как отдельный аналитический режим с исходными предпосылками. Автоматическая согласованность двух масштабов не заявляется, пока не определены преобразования данных.

Полный цикл демонстрации:

1. Задать потребности жителей, начальные денежные остатки, запасы, производственные мощности и ограничения ресурсов.
2. Рассчитать выполнимый план и отдельно показать неудовлетворённые потребности.
3. Проверить наличие средств казны и сформировать назначения без повторного начисления за тот же период.
4. Зарезервировать физический ресурс и средства, затем подтвердить получение либо освободить резерв.
5. Провести расчёт и возврат средств в казну по явному правилу выбранного сценария.
6. Сверить денежные и физические остатки, показать результаты дня и историю операций.

Три экрана: житель видит собственные назначения и получения; оператор — потребности, ресурсы и дефициты; аудитор — проводки, основания решений и результаты сверок. Для публичного просмотра использовать агрегаты, а не персональные покупки.

Сценарии: базовый оборот; сохранение части средств жителями; падение доступной энергии; увеличение потребностей; попытка повторить назначение; попытка эмиссии без подтверждённого роста. Дефицит ресурса и недостаток средств должны отображаться раздельно. Дополнительная денежная запись не создаёт физическую энергию или продукты.

## Правила, которые нужно определить до реализации

- Единица Теңге, её минимальная доля, состав базового набора и правила пересмотра нормативов.
- Срок сохранения неиспользованных назначений и допустимые действия при нехватке ликвидности. Не вводить автоматическое сгорание средств как скрытое техническое допущение.
- Когда средства производств возвращаются в казну, какие резервы нужны и как отличать свободный остаток от зарезервированного.
- Что считается подтверждённым реальным ростом, кто его подтверждает и как из него получается допустимая величина эмиссии. Рост и нехватка оборотных единиц — необходимые условия модели, а не готовая формула суммы.
- Правила очерёдности при физическом дефиците. Базовое обеспечение не должно зависеть от рейтинга или занятости; дополнительное вознаграждение учитывается отдельно.

До согласования этих правил допускаются только явно названные экспериментальные сценарии. Их нельзя выдавать за окончательное устройство системы.

## Проверки готовности

- Сумма дебетовых и кредитовых записей каждой операции сходится. Изменение обращения возможно только через отдельную разрешённую операцию эмиссии; технический счёт эмитента учитывается отдельно от обращения.
- Обычные счета, доступные физические запасы и резервы не становятся отрицательными, включая конкурентные и пакетные операции.
- Повтор запроса с теми же параметрами не дублирует результат; тот же ключ с другими параметрами отклоняется.
- Уникальность назначения задана по человеку, периоду и категории. Изменение назначения оформляется явной корректировкой.
- Ошибки исправляются обратной проводкой с указанием основания. Удаление истории не используется для «очистки» балансов.
- Сбой между резервированием и подтверждением не теряет деньги и не создаёт повторную выдачу ресурса.
- Расчёт хранит версию модели, входные данные и статус. Устаревший результат нельзя применить к изменившимся остаткам без повторной проверки.
- Python worker не имеет прав менять денежный журнал. Роль жителя не позволяет просматривать чужие персональные операции.
- Повтор запуска сценария с теми же исходными данными даёт те же экономические результаты. Резервная копия действительно восстанавливается.

## Позиционирование

Ценность Qazna предстоит показать через проверяемую связь потребностей, реальных ресурсов и денежных правил. Само наличие цифровой денежной платформы не является незанятой нишей: например, существует официальный проект [цифрового тенге Национального банка Казахстана](https://nationalbank.kz/ru/page/Digital-Tenge). Он не тождественен экономической модели книги. Заявление об отсутствии аналогов требует отдельного исследования; основанием для MVP служит проверяемая гипотеза, а не предполагаемое отсутствие конкурентов.
