# Preliminary Qazna analysis

Historical plan recorded at the start of implementation on 2 November 2026. See the [README](../README.md) for current capabilities. This document preserves the initial findings and targets; its schedule is not a claim that every milestone has been completed.

The target demonstration date is 16 November 2026, identified by the author as the review deadline for the eGov/eOtinish submission. The project is **Qazna**, with **qazna.org** as its proposed primary name, based on the Tenge economic model from *Tartar and I*. The earlier code lives in a separate Qazna repository; this directory contains the new Rust application, PostgreSQL migrations, tests and development plan. Naming the domain does not assert ownership verification or a deployed website.

## Initial decision

Build a research MVP with synthetic residents, physical resources and auditable accounting. Aim for a reproducible full provisioning cycle and failure scenarios by 16 November. A simulation tests consequences of selected rules; it does not establish applicability to a national economy. The submission review deadline does not imply approval for a government pilot.

At the author's direction, use the intended production stack from the start: Rust, Tokio, Axum, SQLx and PostgreSQL. Python remains the calculation component; React/TypeScript is the future UI. Do not build a temporary Go implementation for later replacement. Use the old Qazna as a source of requirements and tests.

At the time of this initial analysis, the first module implemented persistent history, exact amounts, atomic transfers, idempotency and a local HTTP API. The full economic MVP remained unfinished. The [architecture](architecture.md) and [development guide](development.md) track subsequent implementation.

The 2 November rerun passed internal checks in both basic and extended modes. Comparison against saved JSON covered 4,762 numeric values, with no differences at relative tolerance 1e-10 and absolute tolerance 1e-8. It used the existing temporary environment `/private/tmp/tenge-research-venv`; saved reference results were not overwritten.

The ten-sector model already uses HiGHS. It is a five-year linear model with illustrative sector baskets, prices and capacities. The older observation that a four-sector example lacked a solver does not describe the current ten-sector calculation. Fractional LP capacity and staffing results do not replace planning for indivisible facilities or people. A coverage coefficient is not a fraction of people who may be denied basic provision.

An open issue is visible in the circulation code: after 1,000 initial units circulate and residents retain 100, the treasury holds 900. It cannot make the next 1,000-unit allocation from that balance. Annual physical feasibility does not ensure daily treasury liquidity. Do not automatically issue money to close this gap when the chosen model permits issuance only with verified growth.

## Findings from earlier Qazna

| Component | Implication for the MVP |
| --- | --- |
| Go API, PostgreSQL, postings, roles, governance, audit and tests | Requirements and test scenarios; Go is not part of the new runtime |
| Rust ledger | Executable code exists, including batch movements, event history, snapshots and tests; it is more than an architectural proposal |
| Selection in `cmd/api/main.go` | A gRPC setting selects the remote core; otherwise PostgreSQL, then memory. A connected database does not prove the remote core persists there |
| Rust persistence | Inspected code uses file history and snapshots. `flush()` alone is not equivalent to a separately verified durable-write and recovery design |
| Treasury semantics | Go's ordinary Transfer disallows treasury debits and permits fees. The Tenge profile needs explicit allocation semantics and an explicit no-fee rule |
| Idempotency | Inspected paths return the old operation for a key. Also compare request content and reject changed parameters |
| Batch debits | Go InMemory checks each movement before applying the group. Test multiple debits from one account whose aggregate exceeds its balance before reusing this logic |
| Rust through gRPC | TODOs remain for dimensions and detailed balances; do not assume equivalence with Go |
| `web` | package.json identifies a VitePress documentation site. Economic MVP user screens need separate implementation |
| Qazna standard | NON_GOALS excludes monetary policy and a consumer wallet. Define the Tenge model as a separate application profile |

This was a preliminary review, not a full security audit. Old Go tests stopped before execution because of toolchain incompatibility; old Rust tests were not run. The new Rust application has its own real-PostgreSQL checks in `scripts/check.py`.

## Technology choices

| Layer | Choice | Reason |
| --- | --- | --- |
| API and operations | Rust, Tokio, Axum | One core for MVP and industrial development |
| Persistent data | PostgreSQL and SQLx, one primary database | Atomic postings, reservations, operation state and future work requests |
| Calculations | Python, NumPy, SciPy HiGHS | Reuse the reproducible mathematical model |
| Interface | React, TypeScript, Vite | Resident, operator and auditor views in one application |
| Worker exchange | PostgreSQL jobs and a Python worker | Versioned inputs/results without an additional broker in the MVP |
| Documentation | Repository Markdown; VitePress if published | Architecture decisions, model rules and reproducible instructions |
| Deployment | Local first, then reproducible packaging | Docker was unavailable as a command during the initial inspection; installed PostgreSQL supports isolated tests |
| AI | Optional explanation assistant | A solver assesses feasibility; AI neither signs postings nor decides issuance |

Meet the deadline by limiting scenarios, not by replacing persistent storage with an in-memory financial prototype. Language choice does not establish monetary correctness; rules and invariants need separate verification.

Use exact integer minor units with overflow checks. Transfers use positive i64 values, ordinary balances nonnegative i64 values and PostgreSQL numeric sums. The economic denomination is unresolved. JSON amounts are strings to avoid JavaScript precision loss. Optimization may use floating point, but its results require an explicit rounding rule and renewed constraint checks before authoritative application.

Transaction isolation needs deliberate design and whole-transaction retries where appropriate; naming an isolation level alone is insufficient. References: [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) and [SciPy HiGHS](https://docs.scipy.org/doc/scipy/reference/optimize.linprog-highs.html).

## Proposed demonstration scope

Model one hypothetical settlement, 100 synthetic residents, food/water/energy and 30 simulated days. Define it explicitly as a new educational scenario. Do not obtain it by simply dividing the five-year large-population model: units, period and infrastructure differ.

Retain the five-year ten-sector calculation as a separate analytical mode with its original assumptions. Do not assert automatic consistency across scales until data transformations are defined.

The intended full cycle:

1. Declare needs, initial accounting balances, stocks, capacity and resource constraints.
2. Calculate a feasible plan and display unmet needs separately.
3. Check treasury funds and make allocations without duplicating a period's entitlement.
4. Reserve physical stock and funds, then confirm receipt or release the hold.
5. Settle and return funds to the treasury under an explicit scenario rule.
6. Reconcile monetary and physical totals; show daily outcomes and event history.

Residents should see their own allocations and receipts; operators needs, resources and shortages; auditors postings, decision bases and reconciliations. Public views should show aggregates rather than personal transactions.

Scenarios include baseline circulation, resident savings, reduced energy, higher needs, duplicate allocation attempts and attempted issuance without verified growth. Resource shortage and insufficient funds must remain distinct. An accounting entry creates neither physical energy nor food.

## Economic decisions still required

- Tenge denomination, minimum unit, basic basket and revision of norms.
- Retention of unused allocations and permitted responses to liquidity shortage. Do not silently implement expiring balances.
- When producers return funds to the treasury, which reserves are required and how free and held balances differ.
- What constitutes verified real growth, who verifies it and how it determines a permissible issuance amount. Growth and a shortage of circulating measure are model conditions, not a finished formula.
- Priority rules during physical scarcity. Basic provision must not depend on employment or a personal rating; additional remuneration is separate.

Until settled, use only clearly labeled experimental assumptions, not claims about the final system.

## Readiness criteria

- Every operation balances debit and credit postings. A circulation change requires a separate authorized issuance action; technical issuer balance is distinct from circulating balances.
- Ordinary balances and available physical stock stay nonnegative under concurrent and batch operations.
- Identical retries do not duplicate results; changed content with the same key is rejected.
- Allocations are unique by resident, period and category; amendments are explicit corrections.
- Errors are corrected through linked reversals with a basis, not deletion of history.
- Failure between reservation and confirmation loses neither money nor stock and does not duplicate delivery.
- Calculations retain model version, inputs and status; stale outputs cannot be applied without rechecking current conditions.
- A Python worker cannot write ledger history; a resident cannot view others' personal operations.
- Repeated scenarios produce the same economic results, and backups demonstrably restore.

These are target criteria, including work not yet implemented; consult current architecture for actual readiness.

## Positioning

Qazna's value must be demonstrated through a testable relationship between needs, real resources and monetary rules. A digital monetary platform is not inherently an unoccupied niche: the National Bank of Kazakhstan has an official [digital tenge project](https://nationalbank.kz/ru/page/Digital-Tenge), distinct from the book's economic model. Claims that no alternatives exist need separate research. The MVP rests on a testable hypothesis, not presumed absence of competitors.
